# External project activity

Open **Settings → External activity** and choose **Set up** for each tool you use. Detection is enabled by default, checks local reports every five seconds, and matches only projects already in the catalog. Register your project folders through **Add folder** first. The bridge installation is offline; it preserves existing hooks and PowerShell profiles and keeps dated `.devdock-*.bak` copies beside changed configuration files.

| Tool | Setup and reported activity |
| --- | --- |
| VS Code | Installs the bundled `devdock-local.devdock-activity` VSIX into a standard Windows VS Code installation. Reload existing windows after setup. Reports local workspace folders, editor changes, focus, and terminal process/folder metadata. Version 0.2 requires VS Code 1.93 or later and can relay dev-command output through terminal shell integration. Supports multiple folders; WSL, SSH, containers, virtual workspaces, and non-file URIs are excluded. |
| Codex | Adds user lifecycle hooks in `~/.codex/hooks.json`. Review and trust the DevDock hook definitions in Codex, then reopen the session. In the CLI, `/hooks` opens the hook browser. Supports local Codex sessions; a loaded chat can remain open after switching away. |
| Claude Code | Adds lifecycle hooks to `~/.claude/settings.json` while retaining unrelated settings. Reopen Claude Code after setup. The Claude chat desktop app is not supported by this bridge. |
| PowerShell | Adds a marked block to the Windows PowerShell and PowerShell 7 current-user console profiles. Open new terminals with profiles enabled. Keeps your existing prompt and execution policy. Works in standalone or editor-hosted PowerShell terminals; `cmd`, Git Bash, WSL shells, and sessions started with `-NoProfile` need another integration. |

Codex requires the human user to trust new or changed non-managed hook definitions; DevDock does not write trust records or bypass that review. This requirement comes from the [Codex hook documentation](https://learn.chatgpt.com/docs/hooks). Agent hooks use the documented session start/end, prompt submit, post-tool, and stop events. Claude Code's Windows hook command uses its [documented exec form](https://code.claude.com/docs/en/hooks), with a separate argument list.

Projects display source badges such as **VS Code**, **Codex · working**, **Claude Code**, and **PowerShell**. **Active** and its count use server state: starting, running, unverified, stopping, or still managed by DevDock. This includes detected servers running elsewhere. Open tool sessions and their latest reported use appear in **Recent activity**; an open workspace alone leaves server status stopped and does not count as Active. A detected external server shows its actual port and HTTP URL with **Running elsewhere**, **Open**, and **Stop external server**. Restart is disabled. Start performs a fresh server check and rejects duplicate launches, including requests made before the next automatic refresh. Closing DevDock leaves external servers running.

**Stop external server** explicitly ends the displayed Node/Bun/Deno server processes and their verified workers on native Windows. If several servers are detected for one project, the button targets all displayed servers; multiple ports owned by one process are stopped once. The request includes each displayed PID, creation time, and port. DevDock refreshes the process/listener inventory, verifies the project match, refuses changed identities or server sets, excludes editor/terminal ancestors and protected apps, and rejects a tree also serving another registered project. Before termination it opens process handles and checks exact creation times and executable names, so PID reuse cannot redirect the stop. A failed check or termination displays an error. The row shows Stopping while the operation runs and returns to Start once the external server has stopped. Your editor, chat, and terminal stay open. This stops the runtime without a graceful Ctrl+C hook; use the original terminal if your server needs custom shutdown handling. DevDock does not automatically restart or adopt external servers. You can start a stopped project through DevDock or run its command again in its original terminal.

The native helper supports server-plus-worker target lists on Windows PowerShell 5.1 and skips targets that have already exited at lookup. Failures report a bounded operation stage, PID, and Windows error code when available; raw process command lines and environment values are not logged. `npm.cmd run test:external-stop` verifies native multi-process stopping, stale worker identity rejection before termination, and already-exited worker handling using temporary fixtures.

External server checks run every five seconds. Native Windows listener and process metadata identify the server through a Node/Bun/Deno entry script inside a registered project, or through a connected terminal's verified PID, process ancestry, and working folder. DevDock probes the loopback HTTP address; a listening process without an HTTP response shows **Unverified**. Relative or globally installed entry scripts require terminal metadata to identify the project. Detection of every runtime, remote workspace, or unconnected terminal is not guaranteed. A failed native check retains the last detected state, reports the failure, and blocks new starts until a check succeeds.

To receive VS Code output, choose **Repair** after upgrading the bridge, reload VS Code, and run `npm run dev` again in a terminal with shell integration enabled. The bridge also supports plain `pnpm dev`, `yarn dev`, and `bun dev` commands, optionally followed by `--` arguments. It captures future output of those commands; output produced before capture attached cannot be recovered. An existing server can still be detected and opened without a live output feed. The details panel explains whether output is streaming or remains in the original terminal.

Live badges require a running owner process with a matching creation time. VS Code heartbeats expire after 45 seconds. Agent hooks without a verified owner show **recent** for at most 90 seconds. Tool badges alone do not enter the Active filter. Closed sessions and dead processes lose their badges on the next check; their last activity stays in the saved catalog. An agent's **working** badge describes its last reported event, not CPU activity or a foreground window. A shell path updates at the next prompt. Multiple matches use the deepest registered project path.

Reports live in the existing `%APPDATA%\Local Dev Manager\external-activity` data directory, beside a local enable/disable policy and a list of registered project paths. Activity reports contain source, hashed session ID, owner PID and creation time, folder paths, timestamps, and session state. Hook input is read in memory to select these fields; prompts, source files, unrelated terminal commands, terminal history, and transcripts are not stored. The native server check extracts only an executable script path from Node-family command lines; full command lines and environment values are not returned or saved. No network listener or telemetry is added. Activity reports are bounded to 32 KiB, the newest 500 are inspected, and unchanged report files older than seven days are removed. Heartbeats update presence without moving projects to the top of Recent activity.

VS Code dev output is relayed through bounded local snapshots under `external-activity/output`: at most 128 entries, 4,096 characters per entry, and 128 KiB of entries. DevDock accepts files up to 256 KiB, validates the reporter and terminal lifetimes, and checks every 500 ms. Snapshot files unchanged for two minutes are removed when DevDock checks them. Output enters the same bounded LogManager as servers started by DevDock. Dev-command output may contain sensitive text printed by your project; unrelated commands and input are excluded from capture. Clearing displayed logs does not replay previously consumed output.

Turning **Detect external activity** off clears tool badges and pauses reporters and output capture while preserving recency. Native server checks continue to prevent duplicate starts. **Check now** refreshes tool activity and server state; **Repair** safely reapplies a bridge. For removal, uninstall **DevDock Activity** from VS Code, remove only the `devdock-activity-hook.cjs` handlers from the agent hook files, or remove the marked `BEGIN DEVDOCK ACTIVITY` / `END DEVDOCK ACTIVITY` block from PowerShell profiles. Backups can recover originals; retain later unrelated edits when restoring.

## Verification

`npm.cmd run test:activity` uses generated projects, isolated DevDock data, isolated agent/shell configuration, and an isolated VS Code extensions directory and user-data profile. It installs the actual offline VSIX and activates it in a native VS Code extension host, checks two workspace folders and process identity, and runs a real PowerShell profile bridge while preserving a custom prompt. Real Electron checks controlled Codex/Claude reports, badges, Active and Recent filters, server separation, small-window layout, toggling detection, expired/dead/closed sessions, persistence, invalid IPC, and renderer errors/requests.

`npm.cmd run test:activity -- --skip-native-vscode` runs the Electron and PowerShell checks without installing or launching the isolated native VS Code integration. It verifies that open tool sessions with stopped servers keep the Active count at zero, a started server appears in Active, and stopping it returns the count to zero while retaining Recent activity.

Vitest verifies malformed and oversized report rejection, PID reuse, DevDock descendant exclusion, deepest-path matching, serialized configuration changes and shutdown, durable activity, old settings compatibility, hook/profile preservation, backups, UTF-16 profile migration, offline packaging, and reporter payload redaction. Native Codex/Claude session execution and Codex trust UI are not covered by the isolated smoke test; they require setup in those tools. This validation does not claim every terminal or remote workspace is detectable.

`npm.cmd run test:external-servers` starts a real Vite server with `npm.cmd run dev` inside an isolated native VS Code extension host. It checks actual port/PID matching, startup and reload output, duplicate-start rejection, Open, disabled external Restart, the Stop external server button, 850×600 layout, detection after DevDock relaunch, and survival when DevDock closes. It rejects stale and malformed stop IPC plus a native creation-time mismatch, stops the real server through the UI, checks that its port closes while VS Code and the original terminal stay open, and verifies a subsequent DevDock-managed Start/Stop. The fixture explicitly loads VS Code's bundled PowerShell shell integration if automatic injection is unavailable. It leaves the user's projects, servers, and profiles untouched. Vitest additionally covers malformed output, unrelated process trees, stale/reused owner and parent PIDs, protected app exclusion, another registered project in the same tree, multiport deduplication, IPv4/IPv6 listeners, failed termination, duplicate stop serialization, and fail-closed preflight checks.
